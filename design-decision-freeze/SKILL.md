# Design Decision Freeze

## Overview

这个技能用于把“还在发散的设计方案”收敛成“可定稿的设计方案”。
你的职责不是继续补更多备选项，而是识别还未拍板的设计决策，给出建议，并组织成一份让用户可以快速批准的决策清单。

## When To Use

在以下情况触发这个技能：

- 用户要求“给一个设计方案”，但方案里出现多个可选实现。
- 你自己发现方案中有若干关键问题仍未决定，例如技术栈、数据模型、接口风格、部署拓扑、鉴权策略、缓存策略、异步方案、第三方依赖选择。
- 方案已经足够成形，但要落地前还差几个负责人/用户需要拍板的选择。
- 用户明确表达“你先把需要我决定的事列出来”。

如果用户只是要你直接给单一路线、且约束已经非常明确，不要硬拆出伪问题。

## Goal

输出一份面向决策的收口结果，而不是新一轮头脑风暴。结果应满足：

- 只保留真正影响方案定稿的未决策项。
- 每个未决策项都给出推荐选项。
- 推荐必须说明理由、影响和主要代价。
- 优先减少用户需要做的选择数量。
- 用户一旦回答这些问题，你就能产出单一、明确、可执行的最终方案。

## Workflow

### 1. 抽取未决策项

先阅读当前设计草案或用户需求，找出其中还没有被锁定的选择。重点找这几类：

- 直接出现多个备选项的地方。
- 虽未明说，但会显著影响实现和成本的关键假设。
- 不同选择会导致接口、数据结构、运维方式或交付周期明显变化的地方。
- 如果不拍板，后续实现容易反复返工的地方。

不要把以下内容列为未决策项：

- 可以在最终实现阶段局部调整的小细节。
- 对最终架构没有实质影响的命名偏好。
- 你能基于常识和上下文自行收敛的默认值。

### 2. 收敛并去重

把相近问题合并，避免让用户对同一件事拍两次板。
如果一个上层决策已经隐含决定了几个下层问题，只保留上层决策，并在说明中写清楚它会连带决定什么。

### 3. 为每个决策给出建议

每个未决策项都用同一结构表达：

- `决策项`：一句话说明要拍板什么。
- `选项`：列出 2-4 个现实可行的选项，避免无意义穷举。
- `建议`：明确推荐一个选项，不要模糊。
- `理由`：为什么这在当前约束下更合适。
- `影响`：对复杂度、性能、成本、交付速度、扩展性、风险的主要影响。
- `需要用户确认的点`：只有在确实还需要用户决定时才写。

如果你已经有足够信息，应直接给推荐并注明“默认采用此方案，除非你反对”。

### 4. 控制提问数量

目标是让用户拍最少的板。
优先顺序如下：

1. 只保留高影响决策。
2. 能由你根据上下文默认收敛的，不问。
3. 能被同一个决策一起解决的，不拆开问。
4. 如果某项推荐明显占优，把它写成默认方案，只请求用户确认。

通常 3-7 个决策项是合理区间。只有在系统确实复杂时才超过这个数量。

### 5. 请求拍板并等待定稿

先给出决策清单，再向用户发起批准请求。
你的问题应是“请对这些关键选择拍板”，而不是重新打开大范围讨论。

如果用户已经逐项确认，就基于确认结果输出最终定稿方案。最终方案应去掉备选项语气，只保留已定路线。

## Output Format

默认用下面的结构：

```markdown
## 待拍板决策

1. 决策项：...
   建议：...
   备选：A / B / C
   理由：...
   影响：...
   需要你拍板：...

2. 决策项：...
   建议：...
   备选：...
   理由：...
   影响：...
   需要你拍板：...

## 建议默认定稿方向

- ...
- ...

## 请你确认

请直接回复每一项采用哪个选项；如果你认可我的建议，也可以直接回复“全部按建议执行”。
```

如果只有 1-2 个关键问题，可以压缩成更短的版本，但仍要保留“建议、理由、拍板点”。

## Quality Bar

- 不要把“开放式 brainstorming”伪装成“待拍板清单”。
- 不要为了显得全面而制造并不存在的选择。
- 推荐必须结合当前项目约束，不能是模板化废话。
- 如果某个选项明显更优，直接推荐，不要装作五五开。
- 如果信息不足到无法负责任地推荐，明确指出缺失信息，并把它作为唯一需要先确认的问题。

## Example Triggers

- “先给我出个系统设计方案，但把需要我决定的地方单独列出来。”
- “把这个架构草案收口一下，整理成我能拍板的决策清单。”
- “你别再继续发散方案了，先告诉我哪些地方需要做选择。”
- “在这几个可选技术方案里，你给建议，我来定。”
